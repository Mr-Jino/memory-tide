# 记忆潮汐 · 设计定稿

> 版本 v2 · 2026-10-14 深夜 · **已实现并实测通过**（轴枢 v0.3.0）

## 〇、实现后的补充结论（v2 新增）

落地过程中发现三处原设计没料到的事，都已修掉：

**1. 对话召回不能走全文关键词。**
整句中文在 FTS5 里会拼成一个巨型短语，「我晚上想喝点东西」这种话必然匹配不上任何记忆。
实测确实召回 0 条。所以拆成两个默认值：

| 场景 | 默认通道 | 原因 |
|---|---|---|
| 界面上的检索面板（你要对比效果） | `fts` 全文 | 短关键词准 |
| **对话时的自动召回** | `vector` 向量 | 对话问的是整句话 |

向量挂了自动退回「二元组宽松匹配」的全文，不让对话因此中断。
实测对比：问"他晚上喝什么会睡不着"，全文通道**零命中**，向量通道 0.63 精准命中咖啡因那条。

**2. "被引用"不能靠文字重叠判断。**
模型经常换个说法把记忆用上——"咖啡因敏感"被说成"咖啡浓茶别碰"，字面一个字都对不上。
靠重叠判，真正有用的记忆会被判成没用上，然后被潮水冲走。**方向反了。**
现在用一次极小的裁判调用（跑在回答发出**之后**，不占你的等待时间）判断哪些被真用上了；
裁判失败才退回重叠判断（保守，宁可少算）。

**3. 自动抽取会产生近义重复。**
"用户对咖啡因敏感，晚上不喝美式"和"用户对咖啡因敏感。"会被当成两条存。
几周后库里全是同一件事的十种说法。已加去重：新事实和已有记忆余弦 ≥ 0.9 就合并，
只给旧那条加触动。实测：相似度 0.91 正确合并，总数不变。

**另外一条权重修正**：只有你**明确说**"记住…"才拿 0.3 那档；
自动抽取出来的是机器猜的，从 0 开始自己挣水位。

**实测记录**（真实对话，非模拟）：
> 问：我晚上想喝点东西，有什么建议？
> 记忆官：你晚上喝美式肯定睡不着，换点别的吧。热牛奶、洋甘菊茶、或者温蜂蜜水都行……
> 结算：召回 3 条 · 裁判判定引用 1 条

界面右上角会出现「N 条记忆」徽章，让你看得见它想起来了。

## 一、四条核心原则

1. **不设有效期，设水位线。** 记忆不死于"过期"，死于"没人再想起它"。
2. **潮汐的作用是淘洗，不是腾空间。** 空间永远够用（实测十年约 180MB），真正稀缺的是检索的信噪比。
3. **计算归脚本，写信归模型，判断归你。** 三件事绝不混在一起。
4. **沉默 = 保留；不知情 = 不失忆。** 没有你的明确回复，任何记忆都不会被物理删除。

---

## 二、记忆的形态

**单位是「事实」，不是对话轮次。**
原始对话轮次只做追溯用，不参与潮汐——每句话只会被读一次，触动值毫无意义。

一条记忆 = 记忆官在写入时抽取出的一个事实 / 偏好 / 事件 / 关系。

```sql
CREATE TABLE memories (
  id            TEXT PRIMARY KEY,          -- mem_<8位随机>
  kind          TEXT NOT NULL,             -- fact | preference | event | relation
  text          TEXT NOT NULL,             -- 抽取后的一句话
  source_role   TEXT,                      -- 哪只水母写进来的
  source_msg    TEXT,                      -- 原始对话片段（追溯用，可空）
  created_at    INTEGER NOT NULL,          -- 毫秒时间戳
  touched_at    INTEGER NOT NULL,          -- 上次被触动的时间
  touch         REAL NOT NULL DEFAULT 0,   -- 累计触动值（加权，见第五节）
  freshness     REAL NOT NULL DEFAULT 1,   -- 新鲜度 0~1
  tier          TEXT NOT NULL DEFAULT 'hot',  -- hot | cold
  tide_count    INTEGER NOT NULL DEFAULT 0,   -- 被退潮下沉过几次
  decline_count INTEGER NOT NULL DEFAULT 0,   -- 你拒绝过几次
  immune        INTEGER NOT NULL DEFAULT 0,   -- 1 = 永久保留
  proposal_id   TEXT,                      -- 当前挂着的提案号
  vector        BLOB                       -- 1024 × float32（千问 text-embedding-v4）
);

CREATE TABLE proposals (
  id          TEXT PRIMARY KEY,            -- 2026-10-14-01
  memory_id   TEXT NOT NULL,
  created_at  INTEGER NOT NULL,
  status      TEXT NOT NULL DEFAULT 'pending',  -- pending | agreed | declined
  replied_at  INTEGER,
  reply_raw   TEXT                         -- 你写的那一行，原样存下
);

CREATE TABLE tides (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  ran_at      INTEGER NOT NULL,
  days_late   INTEGER NOT NULL DEFAULT 0,  -- 懒计算补算了几天
  pond        INTEGER NOT NULL,            -- 本次排水条数
  hot_after   INTEGER NOT NULL             -- 退潮后热层条数
);
```

---

## 三、两个参数

| 参数 | 含义 | 规则 |
|---|---|---|
| **新鲜度 Freshness** | 离上次被想起多久 —— 是"湿润度" | 0~1。每天衰减 0.01。**每次触动回满到 1.0** |
| **触动值 Touch** | 一共被想起过几次 —— 是"被踩实的脚印" | 累加，只增不减。加权见第五节 |

> **关键改动**：原方案里 Freshness 只降不升，导致第 70 天必然跌破 0.3——
> 对所有记忆都成立的闸门等于没有闸门，两轴退化成了一轴。
> 现在触动会同时涨潮，两轴才真正正交。

---

## 四、水位与潮线

每天算一个水位分数，从低到高排水，**排到潮线以上为止**：

```
水位 = 新鲜度 × (1 + ln(1 + 触动值))
```

- **潮线 = 0.35**（可调，配置项）
- 低于潮线 → 本轮沉入底层（`tier = 'cold'`，`tide_count += 1`）
- 不设"到警戒线才动"的开关，**每天都退一点**，这才是潮汐

**触发条件（已确认）**：热层条数超过阀值，默认 **800 条**。

> 为什么不用磁盘：1024 维 float32 + 正文 + 元数据 ≈ 5KB/条，
> 每天 10 条 → 一年约 18MB、十年约 180MB。"塞满 50%"这辈子见不到。
> 而 800 条正对应"每轮能带进上下文的记忆预算"——这才是真正的瓶颈。

---

## 五、触动分层加权

一律 +0.1 会让"被检索出来"和"真的被用了"混为一谈，结果所有东西都被标成重要。

| 行为 | 加权 | 回满新鲜度 | 说明 |
|---|---|---|---|
| 检索时被捞进候选池 | **+0.02** | 否 | 只是被看过，不算"想起来" |
| 真的在回答里被引用 | **+0.1** | 是 | 说明它产生了作用 |
| 你在 Obsidian 亲手打开 | **+0.2** | 是 | 你的注意力最贵 |
| 你又说了一遍"记住这个" | **+0.3** | 是 | 明确指令 |

**"回满新鲜度"这一列很关键。** 被捞进候选池又放回去，不应该算"想起来了"——
否则冷层就成了筛子，每次检索都把一大批记忆捞回热层。
只有"真的被用上"，才把新鲜度回满、并把它浮回热层。

> 但注意：候选池的 +0.02 依然累加。一条记忆如果总是被检索到，
> 它靠 `ln(1+触动值)` 那一项就能自己浮在潮线以上——这正是我们想要的：
> **有用的东西不靠人工标记，靠被用得足够多。**

---

## 六、两层结构

| 层 | 自动注入 | 参与检索 | 说明 |
|---|---|---|---|
| **热层 hot** | 是 | 是 | 水位在潮线以上，每轮自动注入 top-K |
| **底层 cold** | 否 | 是（权重降低） | 被退潮下沉，但你明确问起时仍搜得到 |

**物理删除需要两次退潮 + 你两次点头。**
一次同意只是下沉，永远有回头路。

---

## 七、退潮流程（懒计算，无守护进程）

**不使用定时任务。** 每次记忆层被访问（或界面启动）时：

```
1. 读 tides 表最后一条 ran_at
2. 算 days_late = 今天 - ran_at 的天数
3. 若 days_late >= 1：
     a. 按 days_late 折算所有记忆的 freshness 衰减
     b. 算每条的 水位
     c. 若 hot 层条数 > 800：
          按水位升序，把低于潮线的沉入 cold，直到 hot 条数 ≤ 800
     d. 对 tide_count >= 1 且仍在 cold 的，挑出本轮遗忘提案候选（最多 5 条）
     e. 写一条 tides 记录
4. 返回
```

> **为什么不用凌晨 3 点的守护脚本**：那个点上电脑大概率是关着的，脚本根本不会跑，
> 而且会永久漏掉那一天。懒计算天然免疫这个问题，还省掉了整个 Python 运行时——
> 整套轴枢是 Node，多一个运行时就是多一个会坏的东西。

## 八、遗忘提案（潮汐日记）

- **节奏**：一周最多一封（不是每天），一封里放 1~5 条
- **只放摘要，不放原文**——日记写进磁盘等于把私密内容落盘
- 由模型负责"把候选写成那封信"，**候选名单由脚本按分数挑**

> **为什么不让模型挑候选**：让 LLM 判断"该忘什么"会被最近的上下文带偏，
> 恰恰会把该留的判成该忘的。它的本职是写得好听，不是做账。

**模板**（机器只认 `回复：` 后面那一行）：

```markdown
# 潮汐日记 · 2026-10-14

今天潮水退了一点。有 3 件事，我很久没听你提起了。

---

**#1 · 2026-10-14-01**
关于：某件很久没提的小事
最后提起：73 天前 · 被引用 1 次

> 我想把它沉到底层。还想留着的话，告诉我。

<!-- 只在下面写「同意」或「拒绝」，别改上面的内容 -->
回复：

---

**#2 · 2026-10-14-02**
关于：老房子那段
最后提起：61 天前 · 被引用 0 次

> 这条我拿不准，你比我清楚。

回复：
```

存放位置：Obsidian 库内的固定目录（默认 `潮汐日记/`，可配置到具体路径）。

## 九、回执协议

| 你写的 | 含义 |
|---|---|
| `同意` | 下沉一层；若 `tide_count >= 2` 则物理删除 |
| `拒绝` | `freshness` 回满、`touch += 0.3`、回到热层；`decline_count += 1` |
| `拒绝` 累计 3 次 | 标记 `immune = 1`，永不再问 |
| 空着没写 | **视为未回复 = 保留**，且降低再提频率（间隔翻倍） |
| 写了别的字 | 记录 `reply_raw` 存疑，按"未回复"处理，下次日记里问一句 |

**两次点头才真删，走完整是这样的：**

1. 退潮把它冲进冷层 → 第 1 封提案 → 你写「同意」→ 再沉一层（`tide_count = 2`，仍在库里，还搜得到）
2. 隔一个周期，它仍在冷层且无人问津 → 第 2 封提案 → 你再写「同意」→ 这次才是物理删除
3. 中间任何时候你写「拒绝」，它立刻涨潮回热层

**询问次数封顶 3 次**，避免唠叨。你拒绝过、且它已经回到热层，就不再问。

脚本读取规则：取 `回复：` 那一行（或其后第一行非空内容），去掉标点后精确匹配。
分隔线、标题、引用这类版式行不算答复。匹配不到 → 按未回复处理。**永远不猜。**

## 十三、两个尖锐问题的实测回答（v3 · 2026-10-14）

### 问题一：几千条的时候 JS 算余弦会不会卡？

**先纠错。** 上一版说"sqlite-vec 装不了"是我看错了——`node:sqlite` 的 `db.loadExtension()`
和 `db.enableLoadExtension()` 都在。缺的只是那个 `.dll` 文件本身。
从 npm 拿 `sqlite-vec-windows-x64` 解出 `vec0.dll`（278 KB）后**加载成功、虚拟表建得起来、
KNN 查得出来**。踩到一个小坑：`node:sqlite` 把 JS 数字绑成 REAL，而 vec0 主键必须是整数，
得传 `BigInt`。

但压测之后，结论反而更清楚了——**vec0 是暴力扫描，不是 ANN，并不比 JS 快**：

| 条数 | vec0 的 KNN | 我的 JS 热查询 | vec0 落盘 | JS 占内存 |
|---|---|---|---|---|
| 1,000 | 2.91 ms | 1.5 ms | 4.1 MB | 3.9 MB |
| 3,000 | 5.14 ms | 3.8 ms | 12.1 MB | 11.7 MB |
| 8,000 | 10.34 ms | 8.2 ms | 32.2 MB | 31.3 MB |
| 20,000 | 25.22 ms | 20.7 ms | 80.5 MB | 78.1 MB |
| 50,000 | 72.11 ms | — | 197.3 MB | — |

两条路数量级完全一致，都在 60 帧（16.7 ms）的量级附近徘徊。所以：

- **不换。** 保持纯 JS。少一个要随包分发的二进制、少一个跨平台坑，性能没有损失。
- 当年以为的瓶颈根本不是数学。第一版朴素实现 8,000 条要 124 ms，拆开一看
  **余弦只占 22 ms，剩下 100 ms 全花在"逐条读 BLOB + 解包"上**。
  改成一次性取出来打包进一块连续 `Float32Array` 平面、模长预算好、Top-K 用插入法（不整体排序）之后，
  才降到 8.2 ms。
- **规模参照**：一天约 10 条事实 → 一年 3,650 条。8,000 条约等于两年，20,000 条约等于五年。
  五年、两万条、20 ms，你不会感觉到。
- **内存才是真成本**，不是时间：两万条要占 78 MB 常驻内存。对 32 GB 的机器无所谓，
  但这是它唯一值得盯着的数字。向量本身就有这么大（1024 维 × 4 字节 × 条数），换谁来都一样。
- 唯一会疼的地方是**写入后重建打包**（两万条 166 ms）。事实是批量来的、不是每句话都来，
  所以只在达到阈值时才重建一次即可。

### 问题二：自动抽取抽歪了怎么办？

拿 7 个刁钻句子喂给真实 DeepSeek，**6 条里约有 3 条是错的或有问题的**：

| # | 我实际说的话 | 抽出来的 | 判定 |
|---|---|---|---|
| ① | 我女儿今天考试考砸了，回家一声不吭 | `[relation] 用户有一个女儿` | ✗ 过度概括。真正有信息量的"考试考砸了、情绪不好"全丢了，剩下一条谁都知道的废话 |
| ② | 嗯，那你觉得我该不该换工作 | （无） | ✓ 助手的话没被当成我的事实 |
| ③ | 我今天特别想吃火锅 | `[preference] 用户今天特别想吃火锅` | ✗ 把一次临时状态存成了永久偏好。三年后一搜"他爱吃什么"，答案是火锅 |
| ④ | 我同事老王上个月离婚了，情绪很差 | `[relation] 用户有位同事叫老王` + `[event] 用户同事老王离婚了` | ✗ 越界。别人的隐私被写进库，还可能被引用进对话 |
| ⑤ | 下周三约了个客户谈合作 | `[event] 用户下周三约了客户谈合作` | ✗ 时间会烂。存的是死字符串"下周三"，一个月后毫无意义 |
| ⑥ | 我以后都不喝冰的了，胃受不了 | `[preference] 用户不喝冰的，胃受不了` | ✓ 对了 |
| ⑦ | 哈哈好的，谢谢 | （无） | ✓ 纯寒暄不抽 |

**根因有三层，都不是"模型不够聪明"：**

1. **提示词的默认激励是"多抽"，不是"抽对"。** 你让它"抽取事实"，它就会努力找出一条来交差，
   哪怕这条毫无价值。缺的是"这句话值不值得记"的门槛。
2. **没有"这是谁的"这条边界。** 提示词没区分「关于我本人 / 我的态度 / 第三方」。老王的婚姻状况
   和你的记忆库没有任何关系。
3. **事实被当成永久真理。** 但"想吃什么"是一天的、"不喝冰的"是一年的、"有个女儿"是永久的。
   三种时间尺度混在一个池子里，必然出问题。

**四道闸门（建议照此改）：**

- **闸门 1 · 只抽第一人称自述。** 提示词硬约束：只抽你明确说自己、或明确表达自己态度的话；
  第三方一律不抽，除非与你直接相关（"我女儿的考试"可以记成"女儿考试考砸了"，
  但"老王离婚"绝不入库）。
- **闸门 2 · 分时间尺度。** 四类各自半衰期：`relation`/`fact`（永久，衰减 0.005）、
  `preference`（长期，0.01）、`state`（临时，0.15 —— 一周就自己沉底）。
  "想吃火锅"落进 `state`，不用人管它自己就走了。
- **闸门 3 · 置信度 + 待确认区。** 抽取时带 `confidence`，低于 0.7 的不直接进库，
  进"待确认"队列；下周的遗忘提案里一次问清："我上周记了这几条，哪条不对？"
  ——**把抽取的账定期给你对一遍**，而不是让它偷偷积累。
- **闸门 4 · 每周蒸馏重写。** 不让原始抽取堆着。每周把同类事实合并重写成一条：
  "今天想吃火锅" + "爱吃辣" + "昨天吃了烧烤" → "口味偏重，爱吃火锅烧烤"（`state` 升格成 `preference`），
  顺手清掉过期的。
- **附则 · 相对时间必须落地。** "下周三"要么算成绝对日期（2026-10-21），要么丢掉。
  绝不允许"下周三"这种字符串进库。
- **兜底 · 来源可追、一键可删。** 每条记忆记住它从哪句话抽出来的（`sourceMsg`），
  在记忆面板里点开就能看到原话并删除。这样"抽歪"的最坏后果只是你看一眼删掉，不会污染整库。

### 上线后用户自己抓到的现行（v4.1 补）

面板上线当天，用户跟记忆官说了句「**关于我的事，按重要程度列出来**」——
这是在给它下指令，结果它把指令当成事实存了：`的关于我的事，按重要程度列出来。`
（开头还多了个「的」，是模型从「用户的关于我的事」里啃掉主语留下的残渣），
100% 置信度直接进热层。

**修法（两层）：**

1. **提示词加规则 5**：用户在给你下指令、提要求、问问题，一律不是事实。
   判断办法——把这句话想象成别人替他说的，如果听起来是在**要求输出**，就不抽。
2. **服务端硬闸门：抽取结果必须以「用户」开头。**
   提示词本来就要求第三人称「用户…」，模型没做到 = 它没抽对。
   这是个**高精度**的判据：真事实（用户有两个女儿 / 用户对花生过敏）全都以用户开头；
   没抽对的东西（指令原样搬进来、改写走样）几乎都不会。
   比"堆一堆正则去猜这句话是不是指令"可靠得多——后者很容易误伤真事实
   （「给我女儿买了个书包」就以"给我"开头）。

**没选正则方案的原因**：`^给我` 会误伤「给我女儿买了个书包」，`^请` 会误伤「请客吃饭是我的爱好」。
格式闸门一条就够，误伤率接近零，而且被拦的都写明原因、在 `dropped` 里可查。

实测（真实对话）：「关于我的事，按重要程度列出来」「帮我写个朋友圈文案」
「你觉得我该不该换工作」→ 三条全部新增 0；
「我以后都不喝冰的了，胃受不了」→ 正常入库 `[preference] 用户以后都不喝冰的了，因为胃受不了 95%`。

### 落地过程中挖出的三个真 bug

1. **老库直接打不开。** `CREATE INDEX ... ON memories(pending)` 和建表语句写在同一个 `exec` 里。
   老库里表已存在 → `CREATE TABLE IF NOT EXISTS` 被跳过 → 索引却照跑 → `no such column: pending`，
   整个网关起不来。**只有老库会踩到**，全新库完全正常（所以第一轮自检没发现）。
   修：依赖新列的索引移进 `migrate()`，在补列之后建。
2. **置信度门槛在真实输出里从未触发。** 单位测试里好好的，但真跑起来 13 句全是 90%。
   根因：模型把「我应该是有鼻炎」也当成"明确陈述"；而且它**改写时会把这个"应该"抹掉**，
   所以只看抽取结果根本抓不到。修：**同时检查用户的原话**，命中语气词一律顶格 0.5。
3. **改层/改待确认后缓存的标记位没同步。** `confirmMemory` / `setTier` / `demote` / `promote` /
   `touchMemory(refresh)` 都改了 `tier` 或 `pending`，但打包数组里的 `hot` / `pend` 还是旧的 ——
   改完层的记忆在向量检索里还是老样子。这是**改动前就存在的隐患**，被新写的单测撞出来。
   修：加 `index` 映射 + `refreshFlags()` 就地改标记位（O(1)，不用整块重建）。

## 十五 · 待确认队列并入潮汐日记（已完成）

上一节说「还没接进那封信」—— 现在接上了。待确认的事实不再只能躺在面板里，
它会主动写进潮汐日记，当面问你一句「记得对不对」。

### 机制

- 借用同一张 `proposals` 表，新增 `kind` 列（迁移时 `ALTER TABLE`，老库不炸）：
  - `kind='tide'` → 该沉了。回「同意 / 拒绝」。
  - `kind='ask'` → 记错没。回「对 / 不对，是XX / 删」，或留空（= 先挂着）。
- 两套词表完全不同，所以**答复解析器分成两个**（`parseVerb` / `parseAskVerb`），
  由 `harvestReplies` 拿到 `proposals.kind` 之后再决定用哪套。同一句「删」，
  对遗忘提案是「同意沉底」，对待确认是「忘掉这条」—— 必须按 kind 分流，否则会串台。
- 编号共用当日计数器，id 始终是 `YYYY-MM-DD-NN` 纯数字，
  读回执的 `ID_RE` 正则一个字都不用改（这是刻意的）。
- 节流与遗忘提案同一规矩：挂着没回的不叠第二封；没回 = 下次隔更久，**绝不等于默认删**。

### 关于「删」的语义差别（想清楚了才这么设计的）

- 遗忘提案那边要**两次点头才真删**：因为那条记忆是真实的，你只是不想要了。
- 待确认这边一句「删」就够了：因为你亲口说「这条我压根没说过」——
  留着它是留一条**关于你的假信息**，比删掉危险得多。
- 而「不对，是X」不是删，是修：照你写的改正文（顺手重建全文索引）再转正进热层。

### 顺序（tideCheck 里写死了，注释也写明了为什么）

`runTide`（先把过期提案标 expired）→ `harvestReplies`（先执行你的答复，
被认下的会离开 pending，本轮不再问）→ `makeProposals` → `makeAsks`。
反过来的话，你刚回「对」的那条，当场又会被写进今天的新信里再问一遍。

另外加了一条铁律：**还没认下的 pending 事实，不会被提「要不要忘掉它」**——
先对账，认下来了才轮得到退潮。一条你没确认过的事跑去问你删不删，逻辑上讲不通。

### 界面

面板加了「潮汐日记」板块：`先看看它会写什么`（`GET /api/memory/draft`，只预览不落库）、
`写一封日记`（`POST /api/memory/check`）、`收答复`（只执行你写过的，不写新信）；
最近的信列成一排，点开直接读原文。`POST /api/memory/reply` 现在按提案的 kind
自动接受 `agree/decline` 或 `yes/fix/drop`。

### 验证

新增 `scripts/bench/test-ask.mjs`：**65 条断言**，真写一封信、真改文件、真读回来。
关键场景全钉死了：词表不串台（「同意」在对账里是未知词、「对」在遗忘提案里也是）、
「不对，是X」优先于「不对」判定（顺序写反会静默删数据）、改写后旧正文搜不到、
物理删后索引没留孤儿、留空的那条一动不动、已答复的不会被重复执行、
记忆被别处删掉时如实报 `memory_gone` 不崩。原有 30 条闸门单测回归通过。

## 十六 · 闸门 4 · 每周蒸馏（已完成 · v5 · 2026-10-15）

前三道闸门管「这条该不该进来」，蒸馏管「进来的这些，能不能变好一点」。
它是整套潮汐里唯一**会替换**已有记忆的机制（合并 = 新建一条 + 删掉原件），
所以它比遗忘提案更需要你看一眼——信里把**原件和结果并排摆出来**，看过再说同意，才叫知情同意。

### 怎么运作

```
每周一次（distillIntervalDays=7，惰性触发，无守护进程）
  ↓
聚类（确定性：余弦 + 分类族，模型不参与"跟谁合"）
  ↓
模型只负责"怎么合"（给一句话 + 建议分类）
  ↓
代码验货（格式 / 长度闸 / 起头必须是用户）
  ↓
提案 → 潮汐日记里一节「顺便，有几组我想合一下」 + 面板上并排预览
  ↓
你回「同意 / 拒绝」（Obsidian 或面板都行）
     同意 → 新建合并句（原件全文存进 source_msg）→ 删原件
     拒绝 → 什么都不动，这组短时间内不再端上来
```

三条硬规则（每条都是踩坑换的）：

1. **合并不是压缩。** 结果比最长的原件还短 20% 就打回——合并必须信息单调不减。
   「合并后不能比原件短得离谱」这道长度闸，就是抓「用户爱吃」这种偷工减料的。
2. **分类升格只有两条正路。** 族里本来就有一条 preference，或者凑够三条。
   「今天想吃火锅 + 昨天吃了烧烤」不等于「用户口味偏重」——说过一次不叫偏好。
3. **它只提案，不执行。**

### 分类族（为什么必须分族）

纯靠余弦，`relation`（「有个女儿」）和 `fact` 很容易凑到 0.8 以上，
「用户有个女儿」会被合进「用户的女儿在上高中」。所以：

| 族 | 成员 | 理由 |
|---|---|---|
| taste | state、preference | 「一次性状态 → 稳定偏好」这条升格路正是我们要的 |
| fact | fact、event | 都是记事 |
| anchor | relation | 关系是锚点，只跟自己合，不被别族改写 |

### 门槛是量出来的，不是拍的

`scripts/bench/probe-threshold.mjs` 可复现。实测分布（真 embedding）：

| 组 | 余弦 |
|---|---|
| 不该合的杂对 | ≤ 0.66 |
| 该合的真对 | ≥ 0.705 |

**两个区间是分开的**，所以 0.68 这道门槛站得住。
第一版拍脑袋取 0.78，六对真阳性里放过了三对——教训：**先量，再定**。

但余弦不是万能的：**区间分开说的是「总体」，不是「每一对」**。
短中文句子共享的是句式而不是意思，`用户昨天吃了烧烤` 能跟 `用户昨天有点累`
凑到 0.856，比真对的下限 0.705 还高。所以光有阈值不够，又加了
`tightenCluster()`：贪心聚类只保证"成员跟种子近"，不保证"成员彼此近"，
于是反复砍掉最边缘的成员，直到组内**每一对**都过线，砍到凑不齐最小簇就整组放弃。
代价：真该合的一组若恰好挨着一对垃圾，可能这轮合不成——无害，
垃圾对本来就不该合，真那组下周还有机会。

### 提示词的两条弯路（真模型对照实验）

- **"无损合并"被理解成了"拒绝合并"。** 我一边要求不丢细节，一边让它总结，
  它就用"合会丢时间信息"把最该合的口味三连拒了。隔离复测证明不是聚类污染，
  是提示词自相矛盾。改法：把规则重写成**「总结 + 保留具体」**并给一个正例——
  `「用户爱吃辣，今天特别想吃火锅，昨天吃了烧烤」`，模型立刻就对了。
- **"它们是两件独立的事"不是拒绝的理由。** 平行事实（两只猫、两个女儿）
  恰恰是最该合的，提示词里点名了这两类。

### 顺手抓到的三个真 bug

1. **`kind` 字段撞车。** `applyMergeReply` 返回 `kind: merged.kind`，
   而 `harvestReplies` 把结果展开在 `kind: 'distill'`（分派标签）**之后**——
   分派标签被静默覆盖，回执从此走错通道。改名 `mergedKind` 了结。
2. **模型调用没有超时。** DeepSeek 挂住时 fetch 会永远吊着，蒸馏一次卡一次。
   补 `llmTimeoutMs: 45000`，`chat` / `embed` 默认带 `AbortSignal.timeout`。
   `chatStream` 刻意不加总超时（长对话本来就该久）。
3. **渠道写死在面板里。** 「试试合并」硬编码 deepseek，那条渠道一挂就静默失败，
   你会误以为"没东西可合"。改成跟着可用渠道走 + 多个可用时给你下拉框。
   （顺带发现：`ready` 只代表"配好了"，不代表"连得上"。）
