# 记忆不死于过期，死于没人再想起

> 写给正在学着用 AI 做个人应用的人 —— 也是写给我自己

我给自己做的这套东西，每周会给我写一封信。上周那封里有这么一段：

```
**#1 · 2026-10-14-01**
关于：那双轮滑鞋的尺码
最后提起：73 天前 · 被引用 1 次

> 我想把它沉到底层。还想留着的话，告诉我。

<!-- 只在下面写「同意」或「拒绝」，别改上面的内容 -->
回复：
```

它不是要删我的文件，也不是我容量不够。它只是觉得这件事我很久没提起了，想问问我还留不留。

这封信是整个项目里最不"技术"的部分，也是我唯一想认真写下来的部分。下面是我这一路上真正想清楚的东西——包括我错的地方。

---

## 一、遗忘被当成了容量问题，其实它是许可问题

几乎所有记忆系统处理"忘"的方式都一样：算个分数，低于阈值就删，理由永远是"上下文有限""存储有限"。

这套逻辑没错，但它默认了一件事：**机器有权决定你的过去。**

我不太能接受这个默认值。不是因为我多愁善感，而是因为记忆系统的错误是**不对称**的：它多记一条，代价几乎为零；它少记一条，你可能永远不知道自己丢了什么——因为你没有那条记忆，也就无从想起。

一件代价不对称的事，默认值应该偏保守。所以我把整个设计反过来了：

| | 主流做法 | 我的做法 |
|---|---|---|
| 遗忘的触发 | 分数低于阈值 → 自动删 | 分数低于阈值 → **写封信问你** |
| 沉默的含义 | 没回应 = 系统自己决定 | 没回应 = **保留**，只是下次隔久点再问 |
| 删除的条件 | 一次决定 | **两次点头**才真删，一次只下沉 |
| 你没说过的事被记错了 | 悄悄留在库里 | 一句话「删」就清掉 |

最后一行是刻意的不对称：**真实的记忆难删，可能是假的记忆好删。** 留着一条"关于你的假信息"，比丢一条真信息危险得多。

这不是产品差异，是立场差异。代价是我必须实现一整套提案、回执、节流的机制——比 `DELETE WHERE score < 0.3` 麻烦十倍。

## 二、记忆的单位不是对话，是事实

第一版我做错了：把每一轮对话当成一条记忆，给它算触动值。

后来发现这毫无意义——**每句话只被读过一次，触动值永远相等，这个参数就是死的。**

所以单位改成「事实」：一条记忆 = 一次抽取出来的、关于某个人的一句话。原始对话只做追溯用，每条记忆都记着它是从哪句话抽出来的，抽歪了点开就能看到原话。

然后是两个参数：**新鲜度**（离上次被想起多久，按分类衰减）和**触动值**（一共被想起几次，只增不减）。

水位 = 新鲜度 × (1 + 对数(1 + 触动值))

用对数压着，是因为"被提起 100 次"不该等于"重要 100 倍"。

**这里我踩过一个自己没料到的坑。** 我最初让新鲜度只降不升，结果第 70 天所有记忆都会跌破潮线——一个对所有记忆都成立的闸门等于没有闸门，两个参数退化成了一个。修法：真的被用上时，新鲜度回满。两个轴才真正独立。

还有一条更细的、我认为是这套设计里最值钱的判断：**"被检索到"不等于"被想起"。**

检索时被捞进候选池，只加 0.02 且不回满新鲜度；真的在回答里被用上，才加 0.1 并回满。因为如果被捞一次就算"想起来"，底层记忆就是个筛子——每次检索都把一大批东西捞回热层，分层等于白做。

判断"到底有没有被用上"是个坑：模型经常换个说法把记忆用上，"咖啡因敏感"被说成"咖啡浓茶别碰"，字面一个字都对不上。所以我在回答发出**之后**（不占用户等待时间）跑一次极小的裁判调用；裁判挂了才退回文字重叠比对——那个偏保守，会把真用上的判成没用上，方向至少是安全的。

## 三、我错了三次，数字都在这里

写这一节，是因为我读别人的项目时最想看的不是他做对了什么，而是他错在哪儿、怎么发现的。

**第一错：阈值是拍脑袋拍的。**

做蒸馏（把一周的碎事实合并重写）时需要一个"多像才算同一件事"的门槛，我拍了个 0.78。

然后把真实 embedding 跑出来量了一遍：不该合的杂对最高 0.66，该合的真对最低 0.705。两个区间是分开的——0.68 就够，而我拍的 0.78 让六对真阳性里放过了三对。

教训很朴素：**先量，再定。** 门槛这种东西没有"差不多"，只有"量过"和"没量过"。

**第二错：抽取提示词的默认激励是"多抽"，不是"抽对"。**

拿 14 句刁钻的真实句子喂进去，7 条是错的或有问题的：

- 「我今天特别想吃火锅」→ 被存成**永久偏好**。三年后一搜"他爱吃什么"，答案是火锅
- 「我同事老王上个月离婚了」→ 别人的隐私被写进库，还可能被引用进对话
- 「下周三约了个客户」→ 存的是死字符串"下周三"，一个月后毫无意义
- 「我女儿今天考试考砸了」→ 抽成"用户有一个女儿"，真正有信息量的情绪全丢了

根因不是模型不聪明，是三件事没做：没有"值不值得记"的门槛、没有"这是谁的"边界、把三种时间尺度（一天／一年／永久）混在一个池子里。

改完四道闸门之后，同一批句子：**14 条里 7 条错 → 8 条全对。**

其中最有用的是一条格式规则：**抽取结果必须以用户的名字开头。** 提示词本来就要求第三人称，模型没做到就是没抽对。它比"堆一堆正则去猜这句话是不是指令"可靠得多——`^给我` 会误伤「给女儿买了个书包」。

改的时候还过度纠正过一次：第一版规则写"第三方的事一律不抽"，结果连「女儿下个月钢琴比赛」也被一刀切了。改成给出可操作的判据——「这件事会不会影响这个人的生活节奏」——才恢复正常。**规则的抽象度错一档，就会误伤。**

**第三错：我以为 sqlite-vec 装不了，还写进了文档。**

后来发现是看错了，`loadExtension` 都在，缺的只是那个 dll。装上之后压测，结论反而更清楚：

| 条数 | 扩展的 KNN | 纯 JS |
|---|---|---|
| 1,000 | 2.91 ms | 1.5 ms |
| 8,000 | 10.34 ms | 8.2 ms |
| 20,000 | 25.22 ms | 20.7 ms |

它是暴力扫描，不比 JS 快。少一个二进制、少一个跨平台坑，性能没有损失，所以我不换。

**顺带发现真正的瓶颈根本不在数学。** 第一版朴素实现 8,000 条要 124ms，拆开一看：余弦只占 22ms，剩下 100ms 全花在逐条读 BLOB、解包。改成一次性打包进连续 Float32Array、模长预算好、Top-K 用插入法之后，才降到 8.2ms。

这条比结论本身重要：**你以为的性能问题，八成在数据搬运上。**

## 四、三张可以抄走的卡片

如果你也在做类似的东西，这三块是我认为最值得直接搬走的，而且都可以独立于我这个项目存在。

### 卡片 1 · 写入的四道闸门

```
1. 只抽第一人称自述；第三方不抽，除非它影响本人生活节奏
2. 抽取结果必须以「用户名」开头 —— 格式判据，误伤率近零
3. 分时间尺度：关系/事实 0.004、偏好 0.01、临时状态 0.15（每天衰减）
4. 置信度 < 0.7 不入库，进待确认队列，下周的信里问一句「记得对不对」
附则：相对时间必须落地成绝对日期，落地失败就丢弃
```

**用在哪**：所有"让 AI 记住用户"的项目。这四条解决的是所有记忆系统共同的病——抽歪。
**什么时候别用**：如果你的记忆来自结构化数据（日历、订单、健康记录），根本不需要抽取，直接用。

### 卡片 2 · 计价协议：看过 ≠ 想起

```
候选池被捞出来   +0.02，不回满新鲜度   ← 只是被看过
真在回答里被引用 +0.1，  回满新鲜度   ← 这才算想起
引用判定跑在回答之后；判定失败退回字面重叠（保守，宁可少算）
```

**用在哪**：任何 RAG、任何"把记忆塞进上下文"的地方。
**关键提醒**：如果"被检索到"就给权重，你的冷层永远形同虚设——每次检索都会把一大片东西捞回热层。

### 卡片 3 · 删除的同意协议

```
沉默 = 保留；删除 = 两次点头；拒绝 3 次 = 永久免疫
真实的记忆难删（两次），可能是假的记忆好删（一次）
提案只放摘要、不放原文；候选由脚本按分数挑，模型只负责写得好听
```

**用在哪**：任何有"删除用户数据"动作的系统。
**为什么不让模型挑候选**：让它判断"该忘什么"会被最近的上下文带偏，恰恰会把该留的判成该忘的。它的本职是写得好听，不是做账。

## 五、最小可跑形态：三个文件、一张表、两个数字

我见过太多人在这一步劝退：一上手就是向量库 + 框架 + 编排层，三天没跑出效果就放弃了。

这套东西的最小骨架其实很小：

- **一张表**：`id / text / kind / created_at / touched_at / touch / freshness / tier`
- **一次惰性核算**：每次访问时算「今天 - 上次退潮 = 几天」，折算衰减。**不要 cron**——那个点上电脑大概率是关着的，脚本根本不会跑，还会永久漏掉那一天
- **两个数字**：潮线 0.35、热层上限（我用 800，你从 200 开始就行）

核心逻辑不到二十行：

```js
// 每天一次，惰性触发
for (const m of all) {
  m.freshness -= decayOf(m.kind) * daysLate;      // 按分类衰减
  m.water = m.freshness * (1 + Math.log1p(m.touch));
}
const sinking = all.filter(m => m.water < TIDE_LINE)
                    .sort((a, b) => a.water - b.water);
while (hotCount > HOT_LIMIT && sinking.length) {
  demote(sinking.shift());                         // 只沉底，不删除
}
// 沉下去的，挑几条写进那封信，问一次
```

**第一个建议**：先别上 embedding。先用 FTS 或字面匹配，等你自己真的感到"搜不到"了再上向量。我那 8,000 条 8.2ms 的压测，是给"要不要上向量"这个问题提供的反面证据——瓶颈常常不在数学，在你还没遇到的地方。

**第二个建议**：先让那封信跑出来。信是这套东西里唯一能证明"它真的在想你"的东西，也是你唯一会愿意看第二次的输出。功能可以从简，信不能丑。

## 六、四件我建议你别做的事

1. **别一上来做通用框架。** 我差点做了。最后发现，只为一个人写反而做对了——通用性的每一分，都要用"具体场景的锐度"去换。
2. **别先上向量库。** 上面那张表就是理由。
3. **别信自己拍的阈值。** 0.78 和 0.68 的差别是三对真阳性。
4. **别信自己没验算过的公式。** 写这篇文章时我为了算个例子，把水位公式代进去算了一遍，才发现一个尴尬的事实：

   按潮线 0.35、偏好类衰减 0.01/天——**触动值 0 是 65 天沉底，触动 20 是 91 天。被引用过 20 次和一次没用过，寿命只差 26 天。**

   我以为的"触动值"几乎是个装饰品。真正决定生死的永远是"最后一次被想起是什么时候"。而我的比喻说的是潮水在淘洗——被踩实的脚印应该**更难被水抹平**，那正确的数学不是抬高水位，是降低衰减率。

   这个漏洞还在代码里，我没急着改。一个连作者自己都要靠事后验算才发现的设计缺陷，说明这类系统不该假装自己是通用方案。

## 七、回到那封信

我做这套东西，最初只是想让一个会退潮的记忆库，别把我的话变成一堆永不删除的记录。后来发现真正要解决的不是"记不住"，是"记太住"——一个什么都忘不掉的系统，等于什么都没记住，因为它不会取舍。

所以最后落在一个很朴素的判断上：

**沉默应该意味着保留，而不是意味着遗忘。**

机器可以提醒我"这件事你很久没提了"，但它不该替我决定那件事不重要。重要的东西不一定是被常常提起的东西——有些东西一个人一辈子只会说一次。

那封信问的其实不是"要不要删"，是"你还记得吗"。

如果你也在这条路上，我给一个今晚就能做的起点：写下你第一个记忆表，两个参数，一个 0.35 的潮线，然后让它给你写第一封信。别急着做面板、别急着上向量、也别急着开源——先看看那封信你敢不敢读第二遍。
